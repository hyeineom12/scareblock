# scareblock

2026-2 데이터사이언스프로젝트 (캡스톤 디자인)

## 우리가 만들고 있는 것

**지연 기반 다중 민감 콘텐츠 사전 차단 프레임워크**

scareblock은 유튜브 영상을 **3초 늦게 재생**하고, 그 3초 동안 위험한 장면이나 소리를 먼저 찾아 사용자가 보기 전에 가리는 시스템이다.

첫 번째 구현 대상은 **갑툭튀(jump scare)**다. 갑툭튀는 소리와 화면이 갑자기 함께 등장하기 때문에, 현재 재생 중인 영상을 그대로 분석해서는 사용자가 보기 전에 막기 어렵다.

다만 scareblock은 처음부터 갑툭튀 하나만을 위한 시스템으로 설계하지 않는다. **민감 콘텐츠를 여러 종류로 확장할 수 있는 프레임워크**를 목표로 한다.

### 먼저 정한 범위

이번 프로젝트에서 다루는 영상은 **유튜브 일반 업로드 VOD**로 한정한다.

영화·대여 콘텐츠처럼 EME(Widevine)가 적용된 영상은 브라우저에서 픽셀과 오디오에 접근할 수 없기 때문에 평가셋과 데모에서 제외한다. 이것은 구현이 부족해서 생기는 문제가 아니라 **브라우저 DRM 규격 자체의 경계**다. 해당 콘텐츠까지 다루려면 서버 측 사전처리를 전제로 한 별도 아키텍처가 필요하다.

## 핵심 아이디어

### 1. 영상을 3초 늦게 보여준다

갑툭튀는 소리와 화면이 동시에 터진다.

즉, **"지금" 재생되고 있는 영상을 보고 나서 판단하면 이미 늦다.**

그래서 영상을 3초 정도 미뤄두고, 그 사이 AI가 먼저 영상을 읽는다. 위험한 구간이 발견되면 사용자가 그 장면에 도달하기 전에 블러를 준비할 수 있다.

**서버에서 영상을 미리 처리하지 않고 클라이언트에서 실시간으로 처리하려면, lookahead를 확보하기 위한 지연이 필요하다.**

이것이 scareblock이 존재하는 이유이자 핵심 주장이다.

물론 영상 전체를 미리 스캔해서 더 긴 lookahead를 확보하는 방법도 있다. 이 방법은 아래의 [보조 경로 — 사전 스캔](#보조-경로--사전-스캔-선택)에서 별도로 다룬다. 다만 서버 비용과 스캔 시간을 지불해야 하기 때문에 **클라이언트 실시간 경로를 대체하는 방법은 아니다.**

### 2. 민감 콘텐츠를 "종류"가 아니라 "얼마나 미리 알아야 하는가"로 나눈다

scareblock에서는 민감 콘텐츠를 단순히 카테고리별로 나누지 않는다.

중요한 기준은 **위험한 장면을 사용자에게 도달하기 전에 얼마나 미리 알아야 하는가**다.

이 기준에 따라 어떤 탐지 경로를 사용할지 결정한다.

| 클래스 | 카테고리 | 화면상 성질 | 지연 버퍼 | 탐지 경로 |
|---|---|---|---|---|
| **예측 불가형** | 갑툭튀 | 순간 사건 (소리·화면 동시 폭발) | **필수** | 오디오 규칙기반 → YAMNet 학습모델 |
| **지속 상태형** | 유혈 · 거미 · 주사기 · 사이렌 | 수 초간 유지 | 불필요 | CLIP zero-shot · 사전 스캔 |

지속 상태형은 프레임 N에서 탐지하고 N+1을 가려도 늦지 않다.

반대로 지연 버퍼가 꼭 필요한 것은 예측 불가형이다. 그래서 **갑툭튀는 단순히 첫 번째로 구현하는 카테고리가 아니라, 시스템의 제약 조건을 보여주는 대표 클래스(flagship)**다.

### 3. 새로운 카테고리는 최대한 싸게 추가한다

카테고리를 하나 추가할 때마다 별도의 파인튜닝을 하는 대신 **CLIP zero-shot**을 사용한다.

새로운 카테고리는 텍스트 프롬프트만 바꿔서 추가할 수 있기 때문에 확장 비용을 거의 들이지 않을 수 있다. 일정이 밀렸을 때 가장 먼저 포기해야 하는 기능이 되지 않도록 하는 것도 이 설계의 장점이다.

다만 정확도가 부족한 카테고리가 있다면 **1개만 선별해서 YOLO 파인튜닝으로 보강**한다.

## 보조 경로 — 사전 스캔 (선택)

사전 스캔은 scareblock의 핵심 아이디어가 아니다. **필요할 때 추가할 수 있는 선택적 확장 경로**다.

일정이 밀리면 가장 먼저 자를 항목이기도 하므로, 사전 스캔이 빠지더라도 위의 세 가지 핵심 아이디어는 그대로 성립해야 한다.

유튜브 VOD는 실시간 방송이 아니기 때문에, 영상을 로드하는 동안 **GPT-4o/Gemini 같은 헤비 VLM으로 앞부분을 백그라운드에서 미리 훑어 트리거 타임스탬프를 계산**해둘 수 있다.

이 경우 3초 지연 버퍼는 사전 스캔이 아직 따라잡지 못한 구간을 위한 안전망으로 동작한다.

다만 이 방식은 서버 API 비용과 스캔 지연을 추가로 지불해야 한다. 사용자가 영상을 열자마자 재생하는 일반적인 시청 패턴에서는 사전 스캔이 재생 속도를 따라잡지 못할 수도 있다.

따라서 **사전 스캔은 클라이언트 실시간 경로를 대체하는 것이 아니라 보강하는 경로**다.

## 관련 연구와 우리가 다른 점

선행 연구를 조사한 결과, **scareblock과 동일한 조합을 다룬 연구는 확인되지 않았다.**

그렇다고 각 요소가 모두 새로운 것은 아니다. 오히려 대부분의 개별 요소에는 선례가 있다.

그래서 이 프로젝트는 **"우리가 처음 만든 기술"이라고 주장하기보다, 기존에 따로 존재하던 기술과 아이디어를 처음 연결한 구조**라는 방향으로 설명한다.

### 지연 버퍼를 이용한 사전 차단 — PSE 연구에 선례가 있다

가장 가까운 선행 연구 계열은 **광과민성 발작(PSE)** 도메인이다.

이 분야에서는 프레임 버퍼를 사용해 위험한 시각 자극이 사용자에게 도달하기 전에 완화하는 연구가 이미 존재한다.

- [Flikcer: A Chrome Extension to Resolve Online Epileptogenic Visual Content with Real-Time Luminance Frequency Analysis](https://arxiv.org/pdf/2108.09491) — 크롬 확장 + 실시간 영상 분석 + 유해 콘텐츠 차단. **구조적으로 가장 가까운 연구**
- [Parallel scheme for real-time detection of photosensitive seizures](https://www.sciencedirect.com/science/article/abs/pii/S0010482516000123) — 실시간 스트리밍 탐지, 8프레임 버퍼
- [A new adaptive temporal filter: Application to photosensitive seizure patients](https://pubmed.ncbi.nlm.nih.gov/11145469/) — 프레임 메모리 버퍼를 이용한 사전 감쇠
- [Evaluating Conformance of Video Safety Tools for Photosensitive Epilepsy](https://pmc.ncbi.nlm.nih.gov/articles/PMC12249941/) — 해당 도구군의 평가 프레임워크

| | PSE 연구 | scareblock |
|---|---|---|
| **버퍼의 역할** | **시간축 필터링** (플리커 평활화) | **사건 탐지 후 도달 전 차단** |
| 탐지 대상 | 저수준 신호 (휘도 주파수) | **의미론적 사건** (갑툭튀·유혈·거미) |
| 카테고리 | 단일 고정 | 다중 · zero-shot 확장 |
| 버퍼 크기 | ~8프레임 (약 0.3초) | 3초 |

따라서 **버퍼를 사용한다는 사실 자체는 차별점이 아니다.**

버퍼 크기를 단순히 늘린 것도 핵심이 아니다. 차이는 **저수준 신호를 평활화하는 것이 아니라, 버퍼 안에서 의미론적 사건을 탐지한다는 것**에 있다.

> **버퍼를 쓴다는 사실은 새롭지 않다.  
> "의미론적 사건을 lookahead로 잡는다"는 점이 핵심이다.**

### 갑툭튀 오디오 특징 — affective computing에 선례가 있다

"갑툭튀(jump scare)"라는 이름으로 된 논문은 없지만, 02단계에서 사용하는 특징 설계 자체는 이미 연구에서 사용되고 있다.

- [Affective Content Analysis in Comedy and Horror Videos by Audio Emotional Event Detection](https://ieeexplore.ieee.org/document/1521500/) — 공포 영상의 오디오 감정 이벤트 탐지
- [Affective Video Retrieval: Violence Detection in Hollywood Movies](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0078506) — **energy entropy 기반 급작스러운 큰 소리 측정**, **혈흔 탐지**가 표준 특징
- [Affective Video Content Analysis: A Multidisciplinary Insight](https://dl.acm.org/doi/10.1109/TAFFC.2017.2661284) — 서베이
- [Multi-modal learning for affective content analysis in movies](https://link.springer.com/article/10.1007/s11042-018-5662-9)

검증된 특징을 재사용하는 것이기 때문에 이 부분은 안전하게 가져갈 수 있다. 대신 **"우리가 처음 제안한 특징"이라고 쓰지 않는다.**

이 계열 연구와 scareblock의 차이는 목적에 있다. 기존 연구들은 대부분 **오프라인 분석이나 검색**을 목적으로 하고, 재생 중 사용자의 시청에 직접 개입하지 않는다.

### 트리거 워닝 브라우저 확장 — 이미 상용 제품이 있다

이미 비슷한 목적의 브라우저 확장도 존재한다.

- [PhobiaBlocker](https://chromewebstore.google.com/detail/phobiablocker/gjgghmahciffkcelboddbmkjkjchjnfk) — 공포증 이미지·영상 블러. **주변 텍스트 NLP** 기반
- [Trigger Warning Extension](https://chromewebstore.google.com/detail/trigger-warning-extension/emlcofoghclkckaajlejfoegblhahoff) · [Youtube Trigger Warning](https://chromewebstore.google.com/detail/youtube-trigger-warning/dhaighcmggigocehbgigdbmgpkhcekgl?hl=en) · SKIP IT — **크라우드소싱 타임스탬프·메타데이터** 기반

하지만 이 계열은 **영상의 픽셀 자체를 분석하지 않는다.**

따라서 라벨이 없는 영상에는 약하고, 실시간 영상 분석과도 거리가 있다. 심사에서 "이미 있는 것 아닌가?"라는 질문이 나올 가능성이 있는 부분이므로 관련 연구에서 먼저 짚고 넘어간다.

### 그래서, 무엇이 새로운가?

| 주장 | 상태 |
|---|---|
| 지연 버퍼로 사전 차단 | ❌ PSE 연구에 선례 |
| 갑툭튀 오디오 특징 | ❌ affective computing에 선례 |
| 공포증 콘텐츠 블러 확장 | ❌ 상용 제품 존재 |
| **재생 중 개입 (online intervention)** | ✅ 기존 계열은 오프라인 분석이 목적 |
| **lookahead 요구량 기준 아키텍처 분류** | ✅ 선행 사례 확인되지 않음 |
| **의미론적 다중 카테고리 × 브라우저 내 실행 × zero-shot 확장의 조합** | ✅ 조합 자체가 공백 |

  - 평가셋 v1(영상 20개, 갑툭튀 타임스탬프 수동 라벨링 + 확장 카테고리 멀티라벨 동시 태깅)
  - 오디오 특징 추출 프로토타입(RMS, 스펙트럼 플럭스, 직전 정적 구간)
  - **라벨 기준 문서화 — 아래 [클립 추출 규칙](#클립-추출-규칙)을 같은 문서에 포함**

**M1** — 가짜 타임스탬프로 블러가 걸리는 계약 확정.

**정량 기준: 720p에서 드롭 프레임 없이 3초 지연 재생이 60초 이상 유지될 것.**

### 02 · 규칙 기반 탐지 — 돌아가는 첫 버전 (10.02 – 10.15)

여기까지 오면 **논문이 성립한다.** 이후 단계는 전부 성능 개선이다.

따라서 이 단계가 **마지노선**이다.

- **개발 A**
  - 브라우저 실시간 오디오 특징 추출(AnalyserNode)
  - 시크·일시정지·배속 대응
  - "안전 버퍼 채우는 중" 로딩 UI
- **개발 B**
  - 규칙 기반 탐지기(정적 → 음량 급등 + 저음 럼블)
  - 평가 스크립트(precision/recall/F1 + 적시성)

**M2** — 실제 유튜브 영상에서 갑툭튀 자동 블러 — **데모 가능**

### 03 · 학습 모델과 멀티모달 + VLM 비교 실험 (10.16 – 11.05)

이 단계의 목표는 **규칙 기반 탐지보다 나은지 확인하는 것**이다.

그리고 논문의 핵심 표가 여기서 나온다.

- **개발 A**
  - 프레임 캡처 → 시각 특징(컷 전환, 밝기 급변, 전역 모션)
  - Web Worker 추론 파이프라인 + ONNX Runtime Web 연동
  - CLIP 모델 ONNX 변환 및 브라우저 내 프레임 임베딩 추론(1~2fps 샘플링)
  - **WebGPU 미지원 환경(WASM 폴백) 동작 정의**
- **개발 B**
  - 평가셋 확장(영상 50~80개)
  - YAMNet 임베딩 + 경량 분류기 학습 및 ONNX 변환
  - 오디오·영상 융합 방식 비교(early/late fusion)
  - CLIP zero-shot 프롬프트 설계 및 카테고리별 정확도 측정
  - (여유되면) GPT-4o/Gemini API로 동일 평가셋 오프라인 채점 → 상한선 벤치마크

**M3** — 학습 모델이 규칙 기반보다 낫다는 수치 확보(또는 아니라는 결론)  
+ 규칙기반 / 학습모델 / zero-shot VLM **3자 latency-정확도 비교표**

### 04 · 트리거 확장과 개인화 (11.06 – 11.19)

이 단계에서는 **"scareblock이 갑툭튀 전용이 아니다"**라는 것을 보여준다.

CLIP zero-shot 덕분에 비교적 저비용으로 카테고리를 확장할 수 있기 때문에, 이 단계는 **컷 목록에서 제외하고 핵심 기여로 다룬다.**

- **개발 A**
  - 민감도 슬라이더
  - 트리거별 켜기/끄기
  - 블러 모드 / 경고만 모드 선택
  - 설정 저장
  - 첫 실행 안내
- **개발 B**
  - 사이렌(YAMNet 기존 클래스에 임계값만)
  - 거미·피·주사기 등 3종 이상을 CLIP zero-shot으로 동시 커버(파인튜닝 없음)
  - 정확도가 부족한 카테고리 1개만 YOLO 파인튜닝으로 보강

**M4** — 트리거 5종 이상 + 개인 설정 동작 — **확장성 입증**

### 05 · 평가와 사용자 실험 (11.20 – 11.30)

이 단계에서는 **논문에 들어갈 숫자를 전부 확정한다.**

- **개발 A**
  - 실험용 빌드 고정
  - 데모 영상 촬영
- **개발 B**
  - 정량 평가 최종(P/R/F1, 적시성, 지연 시간별 성능 곡선)
  - 실패 사례 분석
  - 카테고리별 성능표(갑툭튀 vs 확장 카테고리, 규칙기반 vs 학습모델 vs zero-shot VLM)
- **공통**
  - 사용자 실험 15~20명(원본 vs 필터 시청, 놀람 정도 자가보고)

**M5** — 논문에 들어갈 표와 그래프 완성

### 06 · 논문과 발표 (12.01 – 12.10)

- 논문 작성 — 서론 / 관련 연구 / 시스템 / 실험 / 한계와 향후 과제
- 발표 자료 + 라이브 데모 리허설
- 저장소 정리, README, 재현 절차
  - 평가셋은 **URL + 타임스탬프 + 라벨만 공개**한다.
  - 유튜브 영상을 내려받아 클립으로 재배포하는 것은 ToS 문제가 있으므로 원본 미디어는 배포하지 않는다.

**M6** — 제출

### 논문에서는 이렇게 프레이밍한다

이 프로젝트를 단순한 **"갑툭튀 차단 시스템"**으로 설명하지 않는다.

핵심은 다음과 같다.

> **"민감 콘텐츠를 lookahead 요구량으로 분류하고 각 클래스에 맞는 탐지 경로를 배치하는 지연 기반 프레임워크. 갑툭튀는 서버측 사전처리 없이는 지연이 반드시 필요한 클래스의 flagship 구현체로 검증한다."**

CLIP zero-shot의 성능이 기대에 못 미치더라도 **"적용 한계를 측정했다"**는 결과가 남도록 논문을 결과 독립적으로 작성한다.

## 클립 추출 규칙

평가셋은 영상당 **5분 이내 클립**으로 자른다.

전체 물량은 5분 × 80개 = 400분으로 감당할 수 있는 수준이지만, **어디를 잘라서 평가하느냐가 숫자의 신뢰도를 결정한다.**

예를 들어 갑툭튀가 있는 구간을 미리 알고 그 주변만 잘라내면, 클립 안에서 갑툭튀가 등장하는 비율이 실제 영상보다 훨씬 높아진다.

그러면 **precision이 실제보다 좋게 나올 수 있다.**

오탐률을 제대로 측정하려면 갑툭튀가 없는 시간이 충분히 필요하기 때문이다.

그래서 클립은 다음 규칙을 따른다.

- 클립 경계를 **사건 기준으로 잡지 않는다.** 무작위 오프셋으로 자른다.
- **갑툭튀가 하나도 없는 대조 클립을 30% 이상 섞는다.**
  - 이 대조 클립이 없으면 05단계에서 precision 수치를 방어하기 어렵다.
  - 대조 클립은 전체 80개 안에서 채운다. 80개에 추가하는 것이 아니다.
  - 따라서 갑툭튀 포함 클립은 56개 이하가 된다.
  - 라벨링 총량은 늘지 않는다.
- 위 규칙은 01단계의 라벨 기준 문서에도 함께 포함한다.

## 기술 전제 (검증 결과)

| 전제 | 상태 | 근거 |
|---|---|---|
| 픽셀 접근 | ✅ | 유튜브는 MSE(`blob:` URL)로 영상을 붙이므로 canvas가 taint되지 않는다 |
| 오디오 접근 | ✅ | 같은 이유로 `createMediaElementSource`가 무음을 뱉지 않는다 |
| DRM | ⚠️ | 일반 업로드 영상은 Widevine 없음. 영화·대여 콘텐츠는 EME로 차단된다 — 한계 절이 아니라 앞쪽 [범위 선언](#먼저-정한-범위)에서 scope로 선언한다 |

### 00단계 콘솔 검증 스니펫

유튜브 영상이 재생되는 상태에서 아래 코드를 실행한다.

`pixel`과 `audio`가 모두 `true`라면 전제를 확정한다.

```javascript
const v = document.querySelector('video');
const c = document.createElement('canvas');
c.width = 320; c.height = 180;
c.getContext('2d').drawImage(v, 0, 0, 320, 180);
console.log('pixel:', c.toDataURL().length > 1000);

const ac = new AudioContext();
const an = ac.createAnalyser();
ac.createMediaElementSource(v).connect(an);
an.connect(ac.destination);
setTimeout(() => {
  const d = new Uint8Array(an.frequencyBinCount);
  an.getByteFrequencyData(d);
  console.log('audio:', d.some(x => x > 0));
}, 1500);
```

## 인터페이스 계약

탐지기에서 재생기로 넘기는 데이터는 **이 배열 하나로 통일한다.**

```javascript
[
  { time: 13.42, category: "jumpscare", confidence: 0.87, duration: 1.2, source: "rule" },
  { time: 48.10, category: "siren",     confidence: 0.64, duration: 3.5, source: "yamnet" },
  { time: 91.20, category: "blood",     confidence: 0.71, duration: 2.0, source: "clip-zeroshot" }
]
```

`source`에는 **어떤 모델이 해당 트리거를 탐지했는지** 기록한다.

이 값을 남겨두면 05단계에서 카테고리별·모델별 성능표를 집계하기 쉽다.

| **CLIP 브라우저 추론 속도** — WebGPU에서는 1~2fps 여유, WASM 폴백은 프레임당 수백 ms | 중간 | 03단계에 WASM 폴백 동작 정의 포함. 미지원 시 사전 스캔 경로로 대체 |
| **CLIP은 단일 프레임 모델** — 시간축 사건인 갑툭튀에는 기여하지 않음 | 낮음 (설계상 의도) | 갑툭튀는 오디오 규칙 + YAMNet 담당. lookahead 분류가 이미 이 경계를 반영 |
| **Where's the Jump 정답지는 영화용** — 유튜브 VOD에 직접 사용 불가 | 낮음 | 라벨 기준 정의용 참고자료로만 사용. "공짜 정답지" 계산에서 제외 |

## 일정이 밀리면 무엇부터 자를까?

모든 기능을 끝까지 가져가는 것보다, **핵심 주장을 지키는 것**을 우선한다.

| 순서 | 항목 | 방식 |
|---|---|---|
| 1st | 헤비 VLM 사전스캔 경로 | API 비교 실험만 남기고 서비스 통합은 제외 |
| 2nd | 개인화 UI | 민감도를 코드 상수로 고정 |
| 3rd | 시각 모달리티(영상 특징) | 오디오 단독으로도 갑툭튀는 잡힘 |
| 4th | 사용자 실험 | 정량 평가만으로 축소 |

트리거 카테고리 확장은 CLIP zero-shot으로 비용이 낮기 때문에 **컷 목록에서 제외**한다.

**마지노선은 02단계다.**

## 협업 규칙

- `main` 직접 푸시 금지. **feature 브랜치 → PR → 리뷰 1인 → merge**
- **코드 작업은 시작할 때 Draft PR을 먼저 열고 assignee를 단다.**
  - 누가 무엇을 잡았는지 보여야 작업이 겹치지 않는다.
  - 커밋이 하나도 없으면 PR을 만들 수 없으므로 빈 커밋으로 연다.
    - `git commit --allow-empty -m "작업 시작"`
  - 작업이 끝나면 Ready for review로 전환한다.
  - 문서 수정 같은 단발 변경은 예외로 한다.
- **이슈는 따로 만들지 않는다.**
  - 논의가 이슈와 PR 두 군데로 흩어지면 한쪽이 방치되기 때문에 PR 한 곳에 모은다.
- 브랜치명: `<타입>/<요약>`
  - 예) `feat/data-loader`
  - 예) `fix/plot-axis`
- 커밋 메시지: **한 줄 명령형**
  - 예) `데이터 로더 추가`
- 비밀값(API 키, 계정 정보)은 커밋하지 않는다.
